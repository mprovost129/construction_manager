# November 24 memory exhaustion and notification routing

Render recorded container out-of-memory failures at 09:28, 09:31, and 09:42 EST,
and another at 15:54 EST on November 23. The web instance had a 512 MB limit.
These were memory kills, not a failed migration or a rejected client invitation.

The affected selection and its PDF were successfully saved and published before
the failures. A read-only, memory-capped subprocess streamed all 6,112,352 bytes
of the stored PDF with peak RSS about 104 MB including Django. The WSGI wrapper
test peaked around 111 MB, and the client detail-page render around 111 MB.
These checks did not reproduce the container-wide failure. The prior logs do
not identify the exact allocating request; do not claim the PDF was corrupt or
that the thumbnail path is proven to be the trigger for these particular kills.

## Remediation

- User approved the existing web instance increase from $7/month (512 MB) to
  $25/month (2 GB, 1 CPU). Render completed the compute rollout at 09:48 EST.
  `render.yaml` records the same plan so a future Blueprint sync cannot undo it.
- Bound preview generation to one decoder per worker. Use JPEG draft decoding
  before allocating full pixels, resize before EXIF transpose, close derived
  images explicitly, and bypass preview decoding above four million pixels.
  Busy or oversized previews serve the authorized original, preserving access
  checks and private/no-store headers. Originals are not modified.
- Recycle Gunicorn workers after 500 requests with 100 requests of jitter to
  release retained allocations without restarting the entire service.
- Add project-route start/response/stream-close memory logs. Only a random
  correlation identifier, code-defined route, process ID, phase/status, and
  memory totals are logged. No client identity, path arguments, names, bodies,
  headers, cookies, or file content are recorded.
- Route internal project notifications to active assigned PMs only. Remove the
  company-administrator fallback for client messages. An administrator assigned
  as a PM can still receive updates; projects without a PM have no automatic
  internal recipients. Existing client notification preferences still apply.
  Private staff conversations continue to use their explicit participants.

## Validation

- Full Django suite: 784 tests passed, including permissions and notifications.
- Production static asset build and changed-file lint checks passed.
- Synthetic local four-request / 18-megapixel JPEG experiment: peak working set
  fell from 669.1 MB to 68.6 MB. These are Windows test-process measurements, not
  whole-service production numbers. The test proves and covers a substantial
  memory hazard even though the exact incident trigger is not retained.
- Tests cover rejecting large PNG decoding, JPEG decoder downsampling, concurrent
  decoder admission, exception cleanup, EXIF orientation, private cache behavior,
  streaming cleanup, privacy-safe diagnostics, and administrator exclusion.

After deployment, check the published selection, its PDF download, client-preview
visibility, health endpoint, and Render memory/restarts. Never reproduce suspected
memory exhaustion against the live web process or send test mail to real clients.
